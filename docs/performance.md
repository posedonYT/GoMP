# Производительность и стабильность под нагрузкой

Как GoMP держит до 1000 игроков, что можно настроить и как это проверить.

## Настройки ядра (`conf.json`, секция `gomp`)

| Ключ | По умолчанию | Что делает |
|---|---:|---|
| `max-reliable-backlog` | `4194304` (4 МиБ, минимум 256 КиБ) | Сколько надёжных данных может ждать отправки одному игроку. Если игрок не принимает данные (зависла игра, плохая сеть), при превышении его отключают, а не копят память. |
| `max-packets-per-second` | `1000` (минимум 100) | Лимит датаграмм с одного адреса. Лишние отбрасываются до расшифровки. Если флуд продолжается 5 секунд подряд, соединение рвётся с причиной `packet flood`. |
| `host-ops-per-tick` | `20000` (минимум 100) | Сколько команд скриптов (Node) ядро выполняет за тик. Остальные выполняются в следующем тике, порядок сохраняется. Тяжёлый скрипт, например спавн 10 000 объектов разом, не растягивает тик. |
| `host-mirror-rate` | `10` (1…tick-rate) | Сколько раз в секунду позиции игроков и машин отправляются в Node. Отправка идёт компактной операцией `updates`. Сущности из события (`playerEnterVehicle` и т. п.) приходят свежими сразу. |

Пример:

```json
"gomp": {
  "tick-rate": 30,
  "max-reliable-backlog": 4194304,
  "max-packets-per-second": 1000,
  "host-ops-per-tick": 20000,
  "host-mirror-rate": 10
}
```

## Хранилище геймода: файлы или Redis

По умолчанию данные лежат в файлах `server-files/data/`, по одному файлу на запись:

```
data/accounts/<login>.json
data/characters/<id>.json
data/tables/<таблица>/<ключ>.json   (дома и т. п.)
data/meta.json                      (счётчики)
```

- Пишутся только изменённые записи (`accounts.save(ch)`), асинхронно, раз в секунду, атомарно (tmp + rename). При ошибке запись повторяется.
- **Миграция.** При первом старте старый `data/gomp-rp.json` раскладывается по файлам и переименовывается в `gomp-rp.json.bak`. Откат: удалить папки `accounts/`, `characters/`, `tables/` и `meta.json`, затем вернуть `.bak` на место.

**Redis** включается одним из двух способов:

- в `conf.json`:

  ```json
  "storage": { "type": "redis", "url": "redis://:пароль@127.0.0.1:6379/0" }
  ```

- переменной окружения `GOMP_REDIS_URL=redis://...`.

Что хранится в Redis:

- Ключи: `gomp:acc:<login>`, `gomp:char:<id>`, `gomp:t:<таблица>:<ключ>`, `gomp:meta`.
- Загрузка при старте идёт через SCAN + MGET. Запись — пачкой в MULTI/EXEC.
- При разрыве соединения клиент переподключается, а несохранённые записи ждут и не теряются.
- Лимиты входа и регистрации тоже хранятся в Redis, поэтому переживают перезапуск сервера.

На VPS (Linux):

```bash
sudo apt install redis-server
```

В `/etc/redis/redis.conf` задайте:

```
appendonly yes
appendfsync everysec
requirepass <пароль>
bind 127.0.0.1
```

Проверить на VPS реальный Redis (тест пропускается без переменной):

```bash
GOMP_REDIS_URL=redis://:пароль@127.0.0.1:6379/15 node --test server-files/packages/freeroam/test/store.test.js
```

На Windows без WSL официального Redis нет, поэтому на этом ПК сервер работает на файлах. Код Redis покрыт тестами на встроенном RESP-сервере (`test/fakeredis.js`).

## Вход и защита от флуда (геймод)

- **Хеширование паролей.** Используется `crypto.scrypt` в пуле потоков libuv. Поток событий Node не блокируется, даже если 1000 игроков входят одновременно.
  - Замер: стресс `-auth`, 1000 входов за 10 с. Пауза ответа Node — 1,04 с, то есть норма при пинге раз в секунду.
  - Старый синхронный вариант давал 3,96 с, а при большей нагрузке хост убивал сторож (10 с).
- **Лимиты по IP** (token bucket, `ratelimit.js`):
  - вход — 10 попыток в минуту;
  - регистрация — 3 за 10 минут;
  - localhost не ограничивается.
  - Повторный запрос, пока идёт проверка пароля, игнорируется.

## Клиент игры

Все действия идут в одном скрипт-потоке, поэтому работа, которая растёт с числом игроков, распределяется по кадрам (`client/game/budget.hpp`):

- **Спавн.** За кадр создаётся не больше 3 педов и 4 машин, ближние первыми. Толпа появляется за несколько кадров, а не одним фризом.
- **Дальние сущности** (дальше 150 м) обновляются раз в 3 кадра, по очереди.
- **Проверка видимости (LOS)** при коррекции позиции стала асинхронной: не чаще раза в 250 мс на педа. Раньше синхронный луч пускался каждый кадр.
- **Сеть.** За кадр обрабатывается не больше 512 датаграмм.
- **Чужие метки карты** удаляются порциями по 60 спрайтов за кадр, полный круг занимает 15 кадров раз в секунду. Раньше было около 1800 нативов в одном кадре.
- **Анимации** не ждут загрузки словаря: анимация запускается в кадре, когда словарь готов.
- **Декор дома** строится по кадрам. Экран остаётся тёмным, пока предметы не на месте.
- **Мировые объекты.** Перемещение, поворот, прозрачность и видимость применяются на месте, без пересоздания объекта.

- **Педы удалённых игроков.** Создаются не больше чем для 100 ближайших игроков (сервер стримит до 128). Если кто-то подошёл ближе самого дальнего на 20 м и больше, дальний пед уступает ему место.

Замер в игре (`GOMP_PROBE=perf`, стресс-сервер, все боты в одной точке радиусом 60 м):

| Ботов рядом | Поведение | FPS | Тик клиента, мс |
|---:|---|---:|---:|
| 40 | смешанное | ~150 | 0,47 |
| 100 | смешанное | ~75 | 0,7 |
| 200 (128 в стриме, 100 педов) | только пешеходы | 82–86 | 0,8 |
| 200 | пешеходы и стрелки | ~80 | 1,1 |
| 200 | пешеходы и водители (40 машин) | ~54 | 1,7 |
| 200 | смешанное: пешеходы, водители и стрелки | **игра падает через 2–5 с** | — |

Последний случай — старая проблема, не связанная с оптимизацией: сборка со старым спавном падала ещё быстрее. По трассировке наш код завершает кадр полностью, а падает движок GTA между кадрами. Причина пока не найдена, нужно отдельное расследование. Воспроизведение:

```bash
./bin/gomp-stress.exe -server-bin bin/gomp-server.exe -bots 200 -duration 300s -profile extreme
```

Затем подключиться игрой к порту 23005.

`/perf` в игре показывает FPS и время тика. В `gomp.log` раз в 5 с пишутся строки `perf ...` и `perf parts_ms population=… net=… remotes=… world=… hud=… ui=…`.

Режим зонда `GOMP_PROBE=perf`: после появления клиент 60 с стоит на месте и пишет эти строки. Его можно запускать, например, против стресс-сервера с ботами.

## Метрики

Админ-эндпоинт ядра — `http://127.0.0.1:22010/metrics.json`, адрес задаётся в `admin-bind`.

| Поле | Норма | Что значит |
|---|---|---|
| `tickP99Ms`, `tickMaxMs` | p99 < 10–15, max < 33 | Время тика. Бюджет при 30 Гц — 33 мс. |
| `ticksOver`, `ticksMissed` | 0 | Тики дольше бюджета и тики, пропущенные из-за отставания. |
| `hostOpsDeferred` | 0 | Команды Node, отложенные из-за `host-ops-per-tick`. |
| `hostSilenceMaxMs` | ≈ 1000 | Самая долгая пауза ответа Node на пинг с момента старта. Больше 2500 значит, что Node блокируется синхронной работой. |
| `hostsDown` | 0 | Потери скрипт-хоста (падение или сторож). Каждая потеря удаляет все сущности скриптов. |
| `net.WriterStalls` | 0 | Сколько раз тик ждал сокет. |
| `net.FloodDropped` | 0 | Датаграммы, отброшенные лимитом пакетов. |
| `net.RelBacklogMax` | десятки | Самая длинная очередь надёжных пакетов у одного игрока. |
| `phaseAvgMs`, `phaseMaxMs` | — | На что уходит тик: inbound, scripts, streaming, sync, flush, hosts и т. д. |

## Стресс-тест

```bash
go build -o bin/gomp-server.exe ./core/cmd/gomp-server
```

```bash
go build -o bin/gomp-stress.exe ./tools/stress
```

```bash
./bin/gomp-stress.exe -server-bin bin/gomp-server.exe -bots 1000 -duration 45s -profile mixed -label my-run
```

- `-auth` — каждый бот сначала входит с паролем (scrypt в Node), это поток входов.
- `GOMP_STRESS_AUTH=sync` — синхронный хеш, чтобы сравнить со старым поведением.

Отчёты сохраняются в `reports/stress-*.md|json`. Там проверки, метрики сервера, фазы тика и задержки бот→бот.

Результаты на этом ПК (Windows, 12 потоков; 1000 ботов работают на той же машине):

| Прогон | tick p50 | tick p99 | tick max | Node: пауза / потери |
|---|---:|---:|---:|---|
| до оптимизации | 6,93 | 15,07 | 19,19 | — |
| после | 5,87 | 13,38 | 19,04 | 1,04 с / 0 |
| после, поток входов `-auth` | 5,83 | 12,45 | 19,12 | 1,04 с / 0 |
| старый синхронный вход | — | — | — | 3,96 с |
| убийство Node посреди прогона (500 ботов) | — | 5,17 | 26,83 | хост поднялся сам за ~3 с |

Пропущенных тиков 0. Операций в Node — 13 тыс./с вместо 33,6 тыс./с.

Цель p99 ≤ 10 мс на этом ПК не достигнута: 1000 ботов делят процессор с сервером. На отдельном Linux VPS запись в сокет идёт пачками (`sendmmsg`), и запас больше.
